agentic-coding-methodology

Context that outlives the chat

A file-based methodology for working with coding agents on projects that run for months and thousands of messages. Practically unlimited context — not because the window grows, but because after every task the relevant knowledge lands in files in the repo. Every fresh session reads them and continues where the last one stopped.

Templates and skills: github.com/Henroxx/agentic-coding-methodology

The problem

Two effects, both familiar to anyone who has worked with an agent for more than a day:

  • A full context window makes access to any single item in it fuzzier. Answers get sharper when the window holds less, not more.
  • Summarizing keeps the what and loses the why. Compaction and auto-extracted memories reliably preserve that a decision was made — and reliably drop the reasoning behind it, which is exactly the part you need two months later.

So this methodology does not rely on the agent remembering anything. Knowledge is deliberately written out into versioned files, each with a defined load behavior — then every session is allowed to forget. What gets lost is only what never mattered.

The loop

One task, one cycle. At the end, the knowledge is in files instead of the chat:

What lives where

Context is the scarce resource, not compute. Every file has a defined load behavior — always, targeted, or on demand — and whatever loads always stays small. That is why index files hold references, not explanations.

FileReadContent
CLAUDE.mdalways, fullyBehavior rules only. No project knowledge, no status, no commands.
docs/agentcontext/PROJECT.mdalways, fullyGoal, status, to-dos, open decisions. Short, with references into DETAILS.
docs/agentcontext/DETAILS.mdtargeted sectionsOne section per concept, with an as-of date and the reasoning. May grow long — it is never read fully.
docs/agentcontext/plans/during that blockApproved plans for larger work blocks. Deleted once done and folded into DETAILS.
docs/agentcontext/HISTORY.mdonly when writingDate, what, why — more verbose than a git log. Optional.
docs/agentcontext/TESTING.mdon changesWhat must work, as a checkable scenario list. Optional.

Reference-instead-of-explanation is the whole trick: PROJECT.md stays small enough to always ride along, without losing knowledge. And because everything is plain Markdown, the structure is tool-agnostic. AGENTS.md is the behavior contract; a thin CLAUDE.md pointer is only needed for Claude Code.

Instruction layers

Rules live on four layers, each with a defined audience. The committed project file is a team contract — it enforces only what the team agreed on. Personal preferences never leak into it.

repo: global/AGENTS.md shared baseline — public, versioned Communication and working-style defaults, valid in every repo. A generic starter, not one person's file. Imported by the local file below.
~/.claude/CLAUDE.md you, on this machine — private A small local file: one @import of the public part, plus your name and machine-private facts below it that never get committed.
<repo>/AGENTS.md the team — committed The collaboration contract for this repo: workflow, code and git rules, docs layout. Ends with a methodology: version stamp.
<repo>/CLAUDE.local.md the person in this repo — gitignored Personal collaboration rules that shouldn't bind teammates. Read automatically by Claude Code.

In solo projects the last split doesn't matter — everything may live in CLAUDE.md. The moment a repo is shared, personal rules move to CLAUDE.local.md.

The skills

Procedures live in skills, not in the always-loaded files: a skill costs one description line of context until it is actually invoked. Rules that must hold on every action (commit style, license checks) stay in CLAUDE.md — skill loading is probabilistic, invariants are not.

/setup-project

Scaffolds the methodology into a repo: two short question rounds, then CLAUDE.md, agentcontext files and the handoff skill — as a single revertible commit. Merges instead of overwriting when files already exist. Free-text argument: a variant name and any info you already want to give.

/handoff

Ends a session cleanly: collects the session delta (decisions, status, learnings), persists it to the right files, and prints a 30–50 line handoff block for the next session — references only, no duplicated content, no secrets.

/update-project

Compares the repo's methodology: stamp with the methodology repo's HEAD, translates the diff into proposed changes, and applies only what you pick. Local adaptations are never silently reverted.

Staying in control

Control doesn't mean being asked more. It means every decision is visible, reversible, and none was taken silently:

  • Nothing bigger without an OK. Plan first — the "yes" turns it into code.
  • No silent decisions. Two viable paths → both are named, with a reasoned recommendation. The human decides.
  • No hidden assumptions. What the agent doesn't know, it asks — or writes down visibly as > **ASSUMPTION:** so it can be corrected instead of sinking.
  • Everything is in git. The setup itself is one commit; one command reverts the whole methodology.

Scaling

PROJECT + DETAILS with jump targets is deliberately centralized structured note-taking. It scales until targeted jumping into DETAILS.md becomes unreliable. Then there are two growth paths, and they complement each other:

  • Knowledge scales via a details/ folder. A section that outgrows targeted reading moves to docs/agentcontext/details/<concept>.md; the reference in PROJECT.md now points to a file instead of a section. PROJECT.md stays the single index either way.
  • Behavior scales via per-module CLAUDE.md files. Module-specific rules go into a small backend/CLAUDE.md — Claude Code loads it automatically when files there are touched. Kept tiny: local rules plus pointers, never knowledge dumps.

The reference principle stays identical in both — only the loading becomes mechanical instead of disciplined.

Principles

The rules the file structure follows from. They hold even if the concrete files are named differently:

Context is the scarce resource, not compute. Defined load behavior per file; what always loads stays small.

The goal is a seamless restart. Could a fresh agent with a small context continue from here? If not, the files are missing something.

Persist immediately. What should be documented at session end is already imprecise at session end. Write inline, don't batch.

The why is worth more than the what. Summaries keep results and lose reasons — so reasons are written explicitly, for decisions, rules, and rejected alternatives.

Show options, then decide. No path is presented as the only one. "How you'd build it under conditions X" is kept separate from "what we do for now, pragmatically".

Delegate heavy exploration. Research that would pull many files into the main window runs in a subagent; only the condensed result comes back.

Extract skills from repetition. A procedure that repeats across sessions becomes a skill — never speculatively.

No document creep. New files only when content truly fits nowhere — then marked TEMPORARY with a deletion condition.

Living documents. Outdated assumptions are removed, not annotated. Documentation you can't trust is worse than none.

Global only after it proved itself. New rules land in the project AGENTS.md; only what carried across several projects moves up a layer.

Adopting it

Everything is plain Markdown and a few hundred lines — take what fits, change what doesn't. The files are living documents, including the ones containing the rules.

# make the skills available globally (adjust the clone path)

# Cursor
ln -s <clone>/skills/setup-project  ~/.cursor/skills/setup-project
ln -s <clone>/skills/update-project ~/.cursor/skills/update-project

# Claude Code
ln -s <clone>/skills/setup-project  ~/.claude/skills/setup-project
ln -s <clone>/skills/update-project ~/.claude/skills/update-project

# then, in any project:
/setup-project
